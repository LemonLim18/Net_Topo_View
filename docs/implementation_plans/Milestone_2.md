## Plan: Real-Time Network Copilot Grounding

Rebuild the Network Copilot around a freshness-first context pipeline instead of the current prompt-plus-tools hybrid that mixes stale baked state, topology-only read tools, and partial RAG. The recommended approach is to make inventory, topology, telemetry, incidents, drift, config history, and change events first-class context products with timestamps and event-driven refresh, then expose them consistently across prompt context, tooling, MCP, and vector retrieval. Without that, the system will continue to answer correctly only by accident and will remain materially behind Cisco DNA Center, Juniper Mist, and Huawei iMaster NCE in operational trustworthiness.

**Steps**
1. Phase 0: Define the authoritative context model and freshness contract before any implementation. Specify the canonical sources for each data domain: planned inventory and planned topology from NetBox or local inventory sync, live topology from crawler and SDN state, telemetry from InfluxDB or Prometheus, config snapshots from config history, security and drift from their respective modules, and knowledge documents from the vector store. This blocks all later phases.
2. In the same phase, define freshness metadata that every source must expose: captured_at, ingested_at, source, scope, confidence, and freshness_class such as live, warm, stale, or missing. This blocks steps 4 through 13.
3. Produce a query taxonomy for the agent so every user question routes explicitly to the correct source combination. At minimum define live-only, inventory-only, planned-vs-live comparison, troubleshooting, change-planning, compliance, and knowledge-heavy classes. This blocks steps 6, 7, 9, and 10.
4. Phase 1: Replace the current static prompt refresh model in [backend/llm/agent.py](backend/llm/agent.py) and [backend/llm/context.py](backend/llm/context.py) with a context assembly layer that rebuilds per turn or per context version instead of relying on a long-lived baked prompt. Keep conversation history separate from environment state. This is the single most important dependency for the rest of the plan.
5. Add context versioning and invalidation. Every topology crawl, NetBox sync, webhook event, deployment, config snapshot, incident, drift detection, and telemetry freshness breach should increment or invalidate the relevant context version so the next agent turn cannot unknowingly reuse stale environment state. This depends on steps 1, 2, and 4.
6. Phase 2: Create dedicated agent read tools for inventory and source-of-truth queries in [backend/llm/network_tools.py](backend/llm/network_tools.py). Add at minimum list_inventory_devices, get_inventory_device, search_inventory_devices, get_planned_topology, and compare_planned_vs_live. These tools must query NetBox-preferred inventory with local DB fallback and must return timestamps and source metadata. This depends on steps 1 through 5.
7. Update the existing topology tools so they become explicit about scope instead of pretending to represent all devices. Replace or extend list_all_devices with scope equal to live, inventory, or both, and require agent-visible source labeling in responses. This depends on step 6.
8. Add explicit freshness and recrawl tools such as get_context_health, get_last_sync_status, trigger_context_refresh, and get_refresh_job_status so the agent can request fresh data instead of silently answering from stale state. This depends on steps 4 and 5 and can run in parallel with step 6.
9. Phase 3: Rewire the context bundle in [backend/rag/context_bundle.py](backend/rag/context_bundle.py) and [backend/llm/context.py](backend/llm/context.py) so it actually uses NetBox or a NetBox client when available, not only the local DB path. Inventory, interfaces, IPs, roles, and planned topology must come from source-of-truth first, with fallback made explicit in the context text and tool responses. This depends on steps 1 through 5.
10. Expand the bundle beyond inventory, telemetry, and SDN so it also includes deployment intent status, config snapshot recency, incidents, threat detections, drift findings, and freshness warnings. The agent should not have to discover critical context by lucky tool choice. This depends on steps 2, 3, and 9.
11. Replace the bundle’s fixed telemetry window with adaptive retrieval. For example, live operational questions should use short windows, trend questions should use longer windows, and incident questions should pull relevant recent anomalies and pre-change baselines. This depends on steps 2, 3, and 10.
12. Phase 4: Build an event-driven refresh fabric across crawl, NetBox webhook, onboarding, manual inventory edits, config deployment, config snapshot creation, security alerts, and drift detections. The key requirement is that these events trigger targeted context invalidation and selective rehydration instead of waiting for the next crawl cycle. This depends on steps 4 and 5.
13. Wire post-event agent refresh or cache invalidation into the existing update paths such as [backend/backend.py](backend/backend.py), [backend/netbox/webhook.py](backend/netbox/webhook.py), [backend/netbox/sync_devices.py](backend/netbox/sync_devices.py), [backend/netbox/api.py](backend/netbox/api.py), deployment completion paths, and any config snapshot writers. This depends on step 12.
14. Add a durable context event log that records what changed, when it changed, which source reported it, and which downstream caches or embeddings were invalidated. This is needed for debugging and for explaining why the agent answered a certain way. This depends on steps 5 and 12.
15. Phase 5: Split RAG into distinct collections and retrieval policies instead of treating all knowledge equally. Separate static documentation, live network state, planned inventory and topology, incidents and alerts, config history, and change outcomes into different stores or logical partitions. This depends on steps 1, 2, and 3.
16. Replace the current keyword-based route logic in [backend/llm/retriever.py](backend/llm/retriever.py) with a retrieval planner that uses query classification, source freshness, and scope. Live state should never lose to a generic PDF, and static docs should never override fresh inventory facts. This depends on steps 3 and 15.
17. Implement incremental and event-driven embedding in [backend/rag/auto_embedder.py](backend/rag/auto_embedder.py). Embed only changed devices, links, interfaces, configs, incidents, or drift results instead of re-embedding only after a full crawl. This depends on steps 12 and 15.
18. Add temporal reranking and source weighting to retrieval. Chunks need captured_at, applicable_vendor, applicable_model, applicable_feature, source_type, severity, and freshness weight so the retriever can prefer relevant and current chunks. This depends on steps 2, 15, and 16.
19. Audit and curate the static knowledge base. The current manually ingested store is too thin to support claims of strong operational knowledge. Add vendor design guides, platform command references, troubleshooting playbooks, standards or SOPs, and advisories, then tag them by vendor, platform family, feature, and trust level. This can run in parallel with step 18.
20. Phase 6: Stop treating MCP as a side experiment. Expand [backend/mcp/resources.py](backend/mcp/resources.py) and related MCP surfaces to expose inventory, planned topology, live topology, telemetry snapshots, config snapshots, incidents, drift, change jobs, and context health. Complete the placeholder config resource so it returns actual snapshots, not stubs. This depends on steps 1, 2, 6, 9, and 10.
21. Add streaming or subscription-oriented MCP resources for topology change, device state change, incident state, deployment state, and telemetry freshness warnings so higher-level agents can consume updates continuously rather than polling stale snapshots. This depends on steps 12 and 20.
22. Define one canonical semantics map between MCP, agent tools, REST APIs, and prompt bundles. If a device exists in inventory but not in live topology, every interface should express that state identically. This depends on steps 6, 7, 9, 10, and 20.
23. Phase 7: Improve the agent decision layer so it explains its grounding and confidence. Every answer about network facts should carry source_used, source_age, and whether the result is planned, live, inferred, or mixed. This depends on steps 2, 4, and 6.
24. Add conflict detection in the answering layer. When planned inventory, live topology, telemetry, and config history disagree, the agent should surface the discrepancy instead of flattening it into a single answer. This depends on steps 7, 9, and 10.
25. Add a policy that certain question classes must call certain tools before answering. A management IP query for a named device should first check inventory and then optionally compare against live discovery. This depends on steps 3 and 6.
26. Phase 8: Build evaluation, observability, and regression protection. Create a benchmark suite of inventory-only, live-only, mixed-state, stale-data, incident, and change-planning questions. Score factuality, freshness, source selection, and conflict handling. This depends on all earlier architecture work.
27. Add operational dashboards for context health: last successful crawl, last NetBox sync, last embedding update, number of stale devices, number of missing mappings, event lag, and retrieval source mix. This depends on steps 12 through 18 and can run in parallel with step 26.
28. Add synthetic and replay-based testing for event storms and partial outages. The agent should remain coherent when NetBox is reachable but InfluxDB is stale, when crawl fails but incidents continue, or when deployment changes inventory faster than scheduled sync catches up. This depends on steps 12, 16, and 26.
29. Phase 9: Build the strategic differentiators needed to beat Cisco DNA Center, Juniper Mist AI, or Huawei iMaster NCE rather than merely imitate them. Add intent memory, change outcome learning, root-cause graphing across planned and live states, cross-domain risk scoring, and policy-aware what-if simulation before changes are approved. This depends on the completion of the core grounding and freshness stack.
30. Add a formal digital-twin layer that unifies planned topology, live topology, intended config, actual config, telemetry trends, incidents, and drift into one graph. Without this, the system will keep acting like a set of disconnected modules with an LLM bolted on top. This depends on steps 9, 10, 17, and 24.

**Relevant files**
- [backend/llm/agent.py](backend/llm/agent.py) — static system prompt assembly, chat loop, and refresh behavior that currently allow stale environment state to persist.
- [backend/llm/context.py](backend/llm/context.py) — builds topology, template, and bundle context; must move from baked prompt mindset to freshness-aware per-turn context assembly.
- [backend/llm/network_tools.py](backend/llm/network_tools.py) — topology-first read tools; must gain inventory, planned-state, freshness, and comparison tools.
- [backend/llm/retriever.py](backend/llm/retriever.py) — current keyword router; must be replaced by retrieval planning based on source class, freshness, and query scope.
- [backend/rag/context_bundle.py](backend/rag/context_bundle.py) — intended fused context path for inventory, telemetry, and SDN; must become authoritative, freshness-aware, and source-of-truth correct.
- [backend/rag/auto_embedder.py](backend/rag/auto_embedder.py) — currently crawl-driven state embedding; must support delta and event-driven embedding.
- [backend/rag/api.py](backend/rag/api.py) — administrative and setup surface for RAG and context bundle; may need status, diagnostics, and reindex controls.
- [backend/mcp/resources.py](backend/mcp/resources.py) — incomplete MCP exposure of topology, devices, and config; must be expanded and corrected.
- [backend/mcp/tools.py](backend/mcp/tools.py) — MCP tool layer; should be aligned with the same semantics and freshness guarantees as REST tools.
- [backend/netbox/webhook.py](backend/netbox/webhook.py) — NetBox event ingress; currently a critical leverage point for immediate context invalidation and refresh.
- [backend/netbox/sync_devices.py](backend/netbox/sync_devices.py) — NetBox to local inventory synchronization; must publish refresh and freshness events.
- [backend/netbox/api.py](backend/netbox/api.py) — local inventory and NetBox-facing API surface; should trigger context invalidation on mutations.
- [backend/netbox/sync_topology.py](backend/netbox/sync_topology.py) — planned topology extraction from NetBox; should be used in planned-state grounding.
- [backend/backend.py](backend/backend.py) — system initialization, crawl orchestration, and existing refresh hooks.
- [backend/crawler/store.py](backend/crawler/store.py) — discovered-state persistence path; should emit targeted change events for grounding and embedding.
- [backend/scheduler/jobs.py](backend/scheduler/jobs.py) and [backend/scheduler/core.py](backend/scheduler/core.py) — periodic refresh paths; should become safety nets rather than the primary freshness mechanism.
- [backend/db/manager.py](backend/db/manager.py) and [backend/db/repositories/device_repo.py](backend/db/repositories/device_repo.py) — inventory, config, and audit persistence; may need versioning, recency accessors, and event log support.
- [backend/knowledge_base](backend/knowledge_base) — static human-curated documents; currently too thin to justify strong knowledge claims.

**Verification**
1. Create a source matrix showing, for each query type, which source should answer it first and what fallback order applies. Validate that management IP and planned-device queries resolve to inventory before live topology.
2. Simulate a NetBox device creation or update event and confirm the agent’s next turn reflects it without waiting for the periodic crawl.
3. Simulate a deployment change, config snapshot creation, incident alert, and drift detection and confirm each one invalidates or refreshes only the necessary context products.
4. Ask benchmark questions that intentionally separate planned from live state and confirm the agent surfaces conflicts rather than collapsing them.
5. Verify that every answer about a device includes source and freshness metadata internally and can expose it in debug mode.
6. Verify that MCP resources and REST tools return semantically aligned results for inventory, topology, config snapshots, and incidents.
7. Measure end-to-end event-to-awareness latency for NetBox changes, crawl changes, deployment completion, and security alerts. Set an explicit service objective and test against it.
8. Build regression tests where the inventory contains planned devices absent from live topology and confirm the agent answers correctly for inventory-only questions and correctly distinguishes them from live-state answers.
9. Build failure-mode tests where NetBox is unavailable, InfluxDB is stale, or the crawler has not run recently, and confirm the agent degrades honestly rather than fabricating certainty.
10. Validate that the vector retriever prefers recent live-state chunks over irrelevant static documents for operational questions, and prefers vendor docs over noisy live chunks for how-to questions.

**Decisions**
- Include: source-of-truth inventory grounding, planned-vs-live separation, event-driven context invalidation, delta embeddings, MCP expansion, retrieval planner redesign, conflict-aware answering, and freshness observability.
- Include: a harsh competitive assessment, because the current architecture is not merely incomplete; it is inconsistent about what constitutes truth and that makes operator trust fragile.
- Exclude from the first execution wave: trying to make the model smarter before making the context trustworthy. Model tuning is secondary to fixing source selection, freshness, and event propagation.
- Exclude from the first execution wave: glossy UI features that do not materially improve grounding or recency.
- Recommendation: treat NetBox or the canonical inventory service as the source of truth for planned state and never let topology tools impersonate inventory tools.
- Recommendation: treat scheduled polling as a fallback mechanism, not the primary means of keeping the agent aware.

**Further Considerations**
1. The current system is not close to being superior to Cisco DNA Center, Juniper Mist, or Huawei iMaster NCE in agentic awareness. The harsh truth is that it still behaves like several good subsystems with weak orchestration semantics, not like a coherent network intelligence platform.
2. Missing superior-platform capabilities today include: true event-driven context refresh, source conflict reasoning, digital-twin graph grounding, incident-aware prompt fusion, config outcome learning, automated advisory ingestion, policy-aware simulation, confidence scoring, and per-answer provenance.
3. A realistic execution strategy is two waves. Wave 1 should make the agent trustworthy and current. Wave 2 should make it strategically better than incumbent controllers through learning loops, deeper causal reasoning, and cross-domain context fusion.
