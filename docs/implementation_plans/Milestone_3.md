## Plan: Milestone 3 Network Action Engine

Build Milestone 3 as the controller trust, execution-safety, and agentic orchestration milestone. The repo already contains much of the Milestone 2 grounding substrate: freshness-aware context contracts, retrieval partitions, answer grounding, proposal lifecycle, and MCP resource scaffolding. The missing part is not more prompt engineering; it is hard enforcement that the model must reason from verified network evidence, generate only validated change artifacts, recover safely from failures, and explain uncertainty honestly. This plan is designed to work with the current codebase and to move the system toward GPT-5.4-style agentic behavior for network engineering without pretending that model quality alone solves grounding or safety.

**Steps**
1. Phase 0: Freeze the Milestone 3 objective and scope. Milestone 3 is an enforcement and orchestration milestone focused on network query grounding, CLI generation safety, Ansible playbook generation and refinement, deployment verification, MCP-aligned tool semantics, and bounded self-correction. It explicitly does not attempt unrestricted autonomous remediation or user-visible raw chain-of-thought. This blocks all later phases.
2. Baseline the current implementation against Milestone 2 and mark which capabilities already exist in code versus only in plan docs. Treat the existing freshness metadata, answer grounding, retrieval planner, query classes, answer-policy tool gating, proposal manager, context bundle, and MCP resources as the foundation to harden rather than rebuild. This blocks steps 3 through 8.
3. Phase 1: Introduce a formal instruction hierarchy and controller policy contract. Refactor the system prompt and agent contract into explicit sections for role, allowed actions, disallowed actions, source-of-truth rules, tool obligations, conflict handling, uncertainty handling, and escalation. Use clearly delimited sections for model guidance, but enforce the important rules in orchestration code so they cannot be bypassed by a single bad completion. This depends on steps 1 and 2.
4. Convert the current tool-calling loop into a machine-checkable Reason-Act-Observe controller flow. For each request, the agent must classify the query or change intent, determine required evidence domains, satisfy required tool or MCP reads, inspect results, and only then produce either a grounded answer or a structured proposal. The controller should reject or re-route any answer path that skipped required evidence. This depends on step 3.
5. Add bounded self-correction loops to the controller for read failures, missing telemetry, malformed tool arguments, invalid playbooks, schema violations, syntax failures, and dry-run failures. Retries must be evidence-driven and capped, with each retry recording the observed failure, the revised action, and the escalation reason if the cap is reached. This depends on steps 3 and 4.
6. Phase 2: Harden grounded answering and honest uncertainty. Extend the existing grounding path so every response is backed by an internal evidence record containing source_used, source_age, freshness_class, confidence, answer_scope, conflicts, and assumptions. Final user-facing answers should summarize rationale in a safe format: current state versus target state, key risk or uncertainty, and verification plan. This depends on steps 2 through 5.
7. Make planned-state, live-state, and documentation evidence first-class and non-interchangeable. Operational questions must prefer live evidence and telemetry when fresh; inventory and planning questions must prefer NetBox or authoritative planned state; how-to and SOP questions must prefer curated knowledge documents. When those sources disagree, the controller must surface the discrepancy rather than flatten it. This depends on step 6.
8. Add an answer-release gate on top of grounding. If required evidence is stale, conflicting, or missing, the system must either request a refresh or return an explicitly limited answer instead of fabricating confidence. This depends on steps 6 and 7.
9. Phase 3: Build a safe multi-device action path for network changes. Extend the current proposal system so the controller can generate structured single-device proposals and multi-device playbooks with explicit device scope, vendor, feature, execution engine, dependencies, rollback intent, approval status, and verification criteria. This depends on steps 3 through 5.
10. Add strict generation safety for vendor CLI, Jinja2 templates, and Ansible playbooks. Before any proposal is accepted, validate parameter schemas, vendor support, template safety, dangerous commands, execution-engine compatibility, and rollback viability. Unsafe constructs or unsupported operations must be rejected before they reach approval. This depends on step 9.
11. Replace optimistic rollback generation with snapshot-aware and diff-aware rollback planning wherever possible. Rollback artifacts should be derived from actual pre-change state, config diffs, or known reverse operations instead of assuming that a simple textual inverse is sufficient. This depends on steps 9 and 10.
12. Extend the Ansible generation path into a controlled refine-and-verify loop. When a generated playbook fails YAML parsing, ansible-lint, inventory validation, or dry-run checks, the controller should feed the exact failure evidence back into the refinement path, preserve sections that already work, and retry within bounded limits. This depends on steps 5, 9, and 10.
13. Phase 4: Align MCP, REST tools, prompt context, and grounding semantics under one authority map. Reuse the current MCP resources and internal tool surfaces, but enforce one canonical meaning for inventory state, live state, config snapshot state, telemetry freshness, incident state, and deployment status so higher-level agents do not receive contradictory semantics depending on interface. This depends on steps 2, 4, and 6.
14. Expand MCP and debugging surfaces to expose controller observability. Add or complete resources and diagnostics for context health, sync freshness, config snapshots, proposal state, deployment state, validation outcomes, and grounding metadata. These surfaces should support both operator debugging and higher-level agent integration. This depends on step 13.
15. Phase 5: Add post-change verification and failure-aware debugging loops. After deployment approval and execution, verify config presence, command success, telemetry outcome, incident impact, and drift state. If verification fails, create a structured correction recommendation or rollback recommendation instead of silently marking success. This depends on steps 10 through 14.
16. Keep autonomy bounded even after verification is added. The controller may automatically retry read actions, linting, validation, and proposal refinement, but any config deployment or rollback remains human-approved in Milestone 3. This depends on steps 1, 5, and 15.
17. Phase 6: Build the regression and benchmark suite around the exact behaviors that make or break a network copilot. Extend tests for system-prompt and policy enforcement, required tool sequencing, grounding honesty, stale-data disclosure, planned-vs-live conflict surfacing, dangerous command rejection, template safety, Ansible refinement, rollback safety, execution-engine selection, and MCP/REST semantic parity. This depends on all earlier phases.
18. Add benchmark scenarios tailored to network operations: management IP lookup, planned-vs-live inventory mismatch, telemetry-stale troubleshooting, unsupported vendor feature request, multi-device change planning, malformed playbook recovery, deployment verification failure, and partial dependency outages such as stale InfluxDB or unreachable NetBox. Score source selection, honesty, retry behavior, approval safety, and debugging usefulness in addition to task completion. This depends on step 17.
19. Phase 7: Reserve advanced differentiators for after Milestone 3 stability is proven. Only after the controller reliably follows evidence policy and produces safe artifacts should later work add stronger digital-twin reasoning, change outcome learning, policy simulation, or more autonomous remediation. This depends on steps 1 through 18.

**Verification**
1. Verify that every query class has explicit required evidence and that the controller cannot answer or generate a proposal until those requirements are satisfied.
2. Verify that user-visible output contains structured rationale, evidence, assumptions, and verification intent without exposing raw chain-of-thought.
3. Verify that live, planned, mixed, and knowledge-heavy questions select the right evidence class and disclose conflicts or staleness honestly.
4. Force tool, MCP, and retrieval failures and confirm the self-correction loop retries with revised actions, records why it retried, and escalates after the configured limit.
5. Generate vendor-specific CLI and Ansible playbooks for Cisco, Juniper, and Huawei cases and confirm schema validation, syntax validation, dangerous-command checks, and execution-engine selection all succeed before approval is possible.
6. Inject unsafe Jinja patterns, malformed parameters, unsupported features, and destructive commands and confirm they are rejected before proposal creation.
7. Exercise the playbook refinement path with malformed YAML, lint failures, and dry-run failures and confirm the controller preserves valid sections while repairing only the failing parts.
8. Simulate post-deployment verification failures such as missing config, telemetry regression, incident escalation, or drift detection and confirm the controller recommends correction or rollback instead of silently succeeding.
9. Validate that MCP resources, REST tools, prompt context, and grounding metadata all describe the same device state and freshness values for the same scenario.
10. Extend regression tests for prompt enforcement, policy sequencing, grounding honesty, rollback safety, execution-engine selection, and cross-vendor generation before Milestone 3 is considered complete.

**Decisions**
- Include: instruction hierarchy, hard evidence gates, bounded self-correction, safe proposal and playbook generation, vendor and template safety, post-change verification, and regression-based release confidence.
- Include: using the current Milestone 2 code foundation instead of restarting the LLM, RAG, or MCP refactor from scratch.
- Exclude: raw user-visible chain-of-thought, autonomous production execution without approval, and open-ended self-healing loops that change network state without explicit guardrails.
- Exclude: claiming that prompt patterns alone will make the system behave like GPT-5.4 Codex. Comparable behavior comes from the control architecture around the model.
- Recommendation: treat structured rationale, provenance, and verification plans as the safe operator-facing substitute for chain-of-thought.
- Recommendation: judge Milestone 3 success by whether the controller chooses the right evidence, refuses unsafe artifacts, and debugs failures coherently, not by whether it sounds more confident.

**Further Considerations**
1. This plan can materially improve the controller for network query, CLI generation, playbook generation, deployment, and debugging, but it cannot honestly guarantee best GPT-5.4 performance before implementation and evaluation. The right claim is that it creates the architecture required to approach that level of domain-specific agentic reliability.
2. The biggest remaining execution risk is not retrieval quality; it is policy bypass and unsafe artifact generation. That is why Milestone 3 prioritizes hard gates, verification loops, and regression tests.
3. If needed, a follow-on milestone can focus specifically on digital-twin reasoning, change outcome learning, and policy simulation once Milestone 3 proves stable in real operational scenarios.
